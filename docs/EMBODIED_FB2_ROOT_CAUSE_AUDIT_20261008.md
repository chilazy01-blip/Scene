## 1. 首先确认：目前实际运行的线路是哪一条

当前实例由 [benchmark.py](../sage/experiments/embodied_expert_task_v2/benchmark.py:25) 构造，关闭视频、屏幕和离屏渲染，显式使用 200Hz 仿真。控制不读取 RGB-D。`TASK_INSTANCE_R1.json` 明示 `source_fidelity_claim=false`、`fb3_generated_scene_transfer=false`。

## 3. 已证实的底层错误：控制器从错误的初始状态开始计算

### 3.1 错误是怎么发生的

固定源版本 `d82844dcec242c82d6b82628ccc45933c3ad5cbd` 的 `locomanip_basic.py:170` 先调用父类 reset 初始化控制器，再将肩/肘关节改成抬臂姿态；之后只有 `sim.forward()`，没有刷新身体控制器缓存。

随后 `sync_env.py:138` 的 `reset_to()` 恢复保存状态、更新观察缓存，也没有刷新身体控制器缓存。robosuite 的 `controllers/parts/controller.py:199` 只在 `new_update=True` 或 `force=True` 时刷新关节位置、速度和质量矩阵。首个命令到达时，这些控制器的 `new_update` 仍是 false。

实际例子：缓存中的肘角为 −0.10rad，恢复后的真实肘角为 −0.35rad，相差 0.25rad（约 14.3°）。第一条手臂命令本来等于真实当前位置，控制器却按旧姿态计算出不该有的位置误差。

### 3.2 证据不是推测

| 身体部分 | 首步记录力矩与真实当前状态应计算力矩的最大差值 |
| --- | --- |
| 左臂 | 11.603399 Nm |
| 右臂 | 9.299664 Nm |
| 躯干 | 0.409621 Nm |
| 双腿 | 0 Nm |

在新建的同版本原生环境中，不运行一次物理积分或 ONNX 推理，保留旧缓存计算出的首步力矩与历史记录**逐项完全相同**。刷新缓存后，力矩与当前状态独立重算结果一致。

进一步逐步核对 C1–C4 的 4,866 个历史物理步：四条轨迹都只在第 0 步出现上述偏差，之后各身体部分的最大重算误差不超过约 1.1×10⁻¹⁴ Nm；手指执行器输入与对应位置命令一致。四次首步执行器输入也完全相同。

证据：[全轨迹力矩审计](/data/wsj/main/scene_runs/codex_trellis_v2/fb2_root_cause_audit_20261008_v1/ALL_TORQUES_AUDIT_R1.json)、[原生缓存复现](/data/wsj/main/scene_runs/codex_trellis_v2/fb2_root_cause_audit_20261008_v1/RESET_CACHE_AUDIT_R1.json)。

### 3.3 修复已验证到什么程度

已准备隔离修复 [controller_cache_refresh_r2.py](/data/wsj/main/scene_runs/codex_trellis_v2/fb2_root_cause_audit_20261008_v1/controller_cache_refresh_r2.py)，在最后一次初态恢复后、第一条命令前强制刷新四个身体控制器。原生 `forward()` 会顺带改变求解器暖启动，r2 因而显式保留原暖启动，避免将另一个变量混入缓存对照。

[真实环境零积分回归](/data/wsj/main/scene_runs/codex_trellis_v2/fb2_root_cause_audit_20261008_v1/CACHE_REFRESH_REGRESSION_R2.json) 已通过：初始时间/q/dq、目标、执行器输入和暖启动保持不变；刷新后缓存与真实状态一致，首步力矩重算误差至多 2.3×10⁻¹⁶ Nm。

修复没有安装到封存物理试验或改写上游文件，也没有实测其后续动态效果。**已经证明“首步力矩为什么错”，还没有证明“修复后 8 秒处就不会碰桌”。**

## 4. 规划器的问题：几何安全与动态安全之间缺了一层

当前 [几何控制器](../sage/experiments/embodied_expert_task_v5/geometric_controller.py:14) 和 [IK 求解器](../sage/experiments/embodied_expert_task_v3/object_relative_ik_r8.py:18) 接收实际 q，不接收实际 dq；几何检查将速度置零。它们可以判断指定姿态是否碰撞，却不能判断当前速度下是否来得及停住。

“hold”主要做两件事：暂停参考阶段编号；IK 不可行时，把当前观测到的手臂姿态作为这一拍保持目标。下一拍又取新的实际姿态。它不是固定一个停止锚点，也没有保证实际速度被及时消除。外层命令平滑器限制命令速度/加速度，不保证实际运动严格跟随命令或拥有足够制动余量。

最新 C4 的可复核事实：

- 参考阶段从 7.56 秒起停在 158，直到 8.295 秒失败，连续约 0.735 秒；手臂仍在运动。
- 最后一拍已有 `command_transition_pending`、`arm_not_settled`，但这些主要阻止参考进度推进，没有阻止危险接近继续发生。
- 最后命令时刻 8.28 秒，真实手指距桌面约 11.002mm，法向速度约 −0.898m/s。按当时速度作局部线性估计，只剩约 12ms；高层命令周期为 20ms。此估计不是未来轨迹预测，但说明仅看间隙明显不够。
- 所检查的命令端点/姿态插值仍有约 11mm 最小间隙，实际动态轨迹却在 8.295 秒穿入桌面约 1.635mm。
- 独立网格支撑点到桌面的距离与原生接触距离一致，误差约 3.12×10⁻¹⁷m。因此这次不是仅凭错误几何查询报告的假碰撞。

可靠运动证据为 `P/wbc_intent_r1/MOTION_DIAGNOSTICS_R2.json`。R1 的距离查询和复制部位标签曾有错误，旧字节保留，但不能继续拿 R1 解释最新碰撞。

另一个真实规范缺口：[IK 的 acceptable/最终 passed](../sage/experiments/embodied_expert_task_v3/object_relative_ik_r8.py:38) 主要检查已生成接触的穿入及手掌误差，没有把配置中的 0.2mm 正间隙作为完整最终验收条件；禁碰容差还与物理门存在约微米量级差异。优化残差里出现一个间隙参数，不等于最终返回值已经满足它。这是需要修复的检查一致性问题，但不能据此声称它单独解释了 C4：C4 已检查姿态的间隙远大于 0.2mm。

## 5. 控制语义和旧诊断也存在问题

当前身体与手指不是一套简单位置 PD：

```text
腿：          tau = kp * (q目标 - q) - kd * dq
手臂/躯干：   tau = M局部 * [kp * (q目标 - q) - kd * dq] + bias
手指：        原生位置执行器，使用其自身增益、阻尼和力矩限幅
```

源 `robosuite_compat.py:48` 只对关闭 torque compensation 的部分使用普通 PD；手臂/躯干走 robosuite `joint_pos.py:231` 的质量矩阵补偿路径。完整保存状态重算已确认实际执行符合这一语义，首步缓存异常除外。

旧 `diagnose_fb2_braking_authority_r1.py:25` 和被动阻尼诊断使用 `delta_tau / kp` 作为手臂“等效位置改变量”，忽略了质量矩阵，换算不正确。在固定状态、未触发限幅的局部比较中，还需先通过局部质量矩阵的逆映射；限幅则须另行处理。

这一错误影响“多大位置修正等效于多少制动力”的解释，不自动否定那些直接施加保存力矩后求得的瞬时加速度数字，也不证明第五阻尼方案有效或无效。`kd/kp` 形式本身不能一概判错，必须看它被用于哪一种推导。

观察和命令还存在已声明的时序：公开 q/dq 通常来自前一个 5ms 子步；原生 ActionEnv 先设置观察再设置当前 goal，部分导航输入对应上一拍 goal。既有审计证明“符合这套源代码顺序”，不等于已证明这套时延对当前接触操作足够安全。精确原专家环境合同缺失时，也不能凭延迟存在就断言与专家不匹配。

## 6. 场景、资产和专家来源不能被当成已经正确的前提

### 6.1 物性数值有来源，仍缺合理性和任务适配验证

实际箱体主体质量 9.855g，加两个把手共 13.5206g；主体外尺寸约 0.195×0.28×0.15m。来源是上游 `ObjectConfig.density=10`，`SceneObject` 将其覆盖到物体几何，不是本项目 TRELLIS 缩放引入的单位错误。模型质量/惯性可以稳定保存，不代表它们符合目标物体。

上游还统一给这些物体设置摩擦 `(1,1,1)`、`solref=(0.001,1)`、`solimp=(0.998,0.998,0.001)`。需按实际接触的 condim、混合规则检查生效参数，不能仅凭配置列表猜测阻力。当前该组主要碰撞体 condim=3，不能把三个摩擦数值都当作已启用的独立阻力。

本轮没有证据把 C4 碰桌归因于箱子质量，也没有擅自改质量。合理做法是先固定任务物性合同，再做有因果解释的敏感性试验。

### 6.2 发现上游任务定义冲突

同一源 `locomanip_basic.py` 中，成功条件要求箱子静止、直立并接触 `shelf_board_1`，但 `task_config()` 和目标对象暴露使用 `shelf_board_3`。实际模型中两块板的高度相差约 0.496m。

这会令使用任务扩增配置的线路和成功判定瞄准不同层，是必须统一的源级问题。当前适配参考已按原生 board_1 成功判定做端点验证，四次失败都发生在抓握前，**尚不能把这个后续目标冲突当作当前碰桌的直接原因**。透明货架支撑几何同样需要在后续图像/碰撞一致性验收中明确核对。

### 6.3 当前专家已经是深度适配版本

原样参考在当前重建模型下，922 个状态中曾有 597 个超过穿入门、502 个涉及禁碰，最大穿入约 20.11mm。后续修复使参考几何通过、终点满足成功条件，但不构成整段动态可执行性证明。这些数字描述的是“参考放进我们的新模型”，不能反推原始数据集的原模型下也同样失败。

现在使用物体相对 IK、阶段推进、上身绝对修复姿态、下身残差和保持/重定位逻辑，已经不是直接调用一个在同一场景有成功正对照的成熟专家。已有其他任务动作重放成功或状态播放成功，都不能替代这个任务、这套模型、这组质量门下的完整成功对照。

C3 的“不可行”也只能解释为当前姿态偏离范围、手掌容差、优化预算和基座位置下没有找到通过的解。它没有证明任务在物理上根本做不到。将保持超时从 3 秒延长，不能替代改变不可行原因。

## 7. 仿真数值：尚未排除，但不要空口归罪引擎

本轮固定 MuJoCo 3.2.6，模型 SHA256 为 `979c529cdaee2867bfefedb54f68af85da2e76509cfc855668f9ae735aba4e93`。`nq=57, nv=55, nu=43, neq=0`，自由根部。模型数组与快照一致；四条轨迹状态有限、前后逐步连续。实际为 5ms 步长、Euler 积分、Newton 求解器，100 次迭代上限、容差 1e-8、椭圆摩擦锥。

这些检查排除了已检查文件/数组的漂移和中途状态拼接，不能证明步长足够小、接触物性合理或闭环稳定。

MuJoCo 的 refsafe 会将正格式接触时间常数限制在不小于两倍步长。因此，对配置时间常数为 1ms 的相关接触，5ms 步长下可能实际受 10ms 下限支配；机器人与环境的混合接触须单独计算，不能一概而论。减半步长时，接触有效软硬度也可能一起变：仅凭结果改善不能直接宣布“积分精度就是根因”。[MuJoCo 3.2.6 接触参数说明](https://mujoco.readthedocs.io/en/3.2.6/modeling.html#solver-parameters)、[refsafe 定义](https://mujoco.readthedocs.io/en/3.2.6/XMLreference.html#option-flag-refsafe)。

若更换积分器，要以固定版本实际源码为准：3.2.6 的 `mj_step2` 支持 implicit/implicitfast，RK4 在 split-step 下退回 Euler；不能引用旧页面的一句话便断言 split-step 一律 Euler。[3.2.6 engine_forward.c](https://github.com/google-deepmind/mujoco/blob/3.2.6/src/engine/engine_forward.c)。本轮未更换积分器。

## 8. 规范和审计为什么没能提前拦住这些问题

现有独立审计能重建保存状态、接触、命令拼装、观察和策略历史，足以复核四次失败；但它把记录的低层 ctrl 当输入，**没有独立重算每个身体控制器按真实当前状态应输出的力矩**，因此遗漏首步缓存问题。审计正确复现一次失败，不能替代验证控制器设计正确。

另有两类规范问题：

- `PHYSICAL_PLAN_R1.json` 声明 `max_xy_drift_m=0.1`、`max_z_drift_m=0.08`，当前物理测量路径没有消费这两个字段。若它们是旧站立诊断遗留项，应从任务合同中明确退役；若有意生效，则要先明确参考系。搬运任务不能机械套用“不准移动 10cm”。当前这是声明与实现不一致，未造成四次误报失败。
- 禁碰与允许接触的穿入上限是不同规则。手碰桌属于禁止接触，即使穿入 1.635mm 小于一般 10mm 穿入上限，仍然应该失败。不能以“MuJoCo 是软接触”为由直接放宽手桌禁碰规则。

四次直接终止原因仍成立：C1 在 3.48 秒手臂超速 6.560855rad/s；C2 在 3.095 秒腕/躯干禁碰；C3 在 9.46 秒保持超时；C4 在 8.295 秒手指/桌面禁碰。它们是不同终止条件，不能统一叫“长时间运行不稳定”。

## 9. 自生成资产、渲染和交付还欠哪些验证
